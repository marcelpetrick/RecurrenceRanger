The picture is consistent: an operator who treats an agent as a fully accountable contractor, not an autocomplete. He states the outcome, insists on a plan, then expects the entire batch delivered, reviewed, committed, pushed and released — with evidence attached. What he does not delegate is judgement about scope: the sharpest corrections in the corpus are about agents doing more than was asked.

The doctrine

Seven principles, ranked by how often he has to say them

Counts are matching prompts / sessions / project paths / tool profiles, measured over every human prompt with this project excluded.

  1. Finish the authorized work, then report

    Not the first step, not a plan to do it later, and not a list of commands for the human to run. When several requests are open, all of them get done.

    “get all done” · “get it done and documented” · “run the commands yourself”

    463 prompts188 sessions95 projects4 profiles

  2. Plan first, say what you understood, then execute

    The plan is written down, options are compared with reasons, and the plan file stays current as the work proceeds. Confirmation happens once, at the direction — not at every step.

    182 prompts120 sessions66 projects4 profiles

  3. Review your own output, then fix every finding

    Code, architecture and documentation are reviewed against the current state, findings are ranked by severity, and then all of them are fixed — each with its own commit and, where a reviewer is involved, its own answer.

    169 review112 self-review64 fix-all4 profiles

  4. Commit atomically, conventionally, with a version bump

    One logical change per commit, a conventional subject, a body that says why, a patch increment in the same commit, and only that change's files staged. In company merge requests the same work is squashed into one conventional commit instead — the boundary is the review process, not the taste.

    128 version108 atomic98 conventional44 projects

  5. One pipeline, run locally, mirrored by CI, then watched

    A committed entry point runs formatting, lint, static analysis, tests and coverage; hosted CI runs that same script rather than a second definition; after the push, the pipeline and the review comments are watched and answered.

    112 local55 hosted24 watch4 profiles

  6. Make the result verifiable

    Tests that exercise real behavior, coverage as a measured number with a gate, and claims backed by something someone else can check: a log, a screenshot, a profiling figure, a command.

    “make stuff test and verifiable” · “if you can make your claim testable, then do”

    100 coverage85 tests46 evidence4 profiles

  7. Ship it, and leave a trace

    Work ends in a push and a public release, and it is linked to the ticket or merge request that asked for it, with the reviewer assigned, labels current and the outcome commented back.

    142 ticket trace72 release81 dependencies4 profiles

Vision check

Where the hypothesis was right, and where it was not

The investigation started with four expected categories. Two survived near the top, two fell to the bottom, and the strongest theme was not on the list at all.

Counter-analysis

Ten antitheses: what this doctrine does not cover

Each card states the gap, why it matters at this scale of agent use, and the smallest thing that would close it. Ordered by how much risk the gap carries in the way he currently works.

01no stopping rule

"Get all done" optimises finishing, never questioning

463 prompts push an agent to complete the batch; almost none ask whether the batch was worth building. The corpus contains features built and then deleted a few sessions later.

Close it: make "should this exist?" a required first line of every plan, and let the agent propose deletion as an outcome, not only addition.

02metric gaming

Coverage is an execution metric pretending to be a quality metric

Coverage is the ninth most repeated theme and is enforced with hard gates. A gate at 98% or even 100% proves lines ran, not that a wrong result would be caught.

Close it: add mutation testing to one repository and compare the surviving-mutant rate with the coverage number. If they disagree, the gate is decorative.

03echo chamber

Self review plus AI review is one opinion, counted twice

Review is the third-strongest theme, but the reviewer is usually the same model family that wrote the code, or the same operator who ordered it. Agreement is cheap and looks like validation.

Close it: review with a different model than the author, prompt for disconfirming evidence explicitly, and keep one human reviewer for anything that ships publicly.

04absent

Security and data retention barely appear at all

Dependencies are updated for freshness (81 prompts), not for vulnerabilities; redaction appears three times; secret scanning, threat modelling and a retention policy for captured prompt data appear essentially never — in a workflow whose by-product is a database of private transcripts.

Close it: secret scanning and an advisory check in the same pipeline that already gates coverage, plus one written retention and deletion rule for collected agent data.

05one-way door

Releases have an accelerator and no brake

"Push and make a public release" appears 72 times. Rollback, deprecation, migration and a changelog written for a reader do not appear in any comparable number.

Close it: one release checklist item — how this gets reverted — and a human-readable changelog entry per release, generated from the conventional commits already required.

06semantics lost

A version per commit turns SemVer into a build counter

128 prompts insist on a version bump in every commit. The result is a number that increments faithfully and communicates nothing: a consumer cannot distinguish a typo fix from a breaking change.

Close it: keep the per-commit counter for traceability, and add a separate released version that only moves when behaviour changes.

07unpriced

Speed is measured; cost, energy and quota are improvised

Profiling gets requested when something feels slow, and quota limits show up as irritation rather than as a metric. Delegation to smaller models (74 prompts) is the right instinct without a number attached to it.

Close it: record tokens and wall time per completed task, and let that decide which model gets the next batch.

08proxy outcome

Tests verify the code, not whether the thing helps anyone

The corpus is rich in engineering verification and thin in acceptance criteria stated from a user's point of view; usability appears mostly as visual polish, accessibility almost not at all.

Close it: one acceptance sentence per feature in the user's own words, checked at the end of the batch alongside the pipeline.

09write-only

Documentation is optimised for the author's reading time

"Crisp", "brief", "not tons" (61 prompts) is good discipline for prose and a poor fit for decision history: why an option was chosen is the part a successor — or the same operator in three months — actually needs.

Close it: keep the README short, and add a one-paragraph decision record per significant choice, which the existing "document the decision" habit already almost does.

10blind after ship

The pipeline is watched; production is not

"Watch the CI" and "overwatch" appear throughout, and they stop at the merge. Logs, metrics, alerts and error budgets for the released software are absent from the corpus.

Close it: for anything with users, one health signal and one alert as part of the definition of done — the same rigour that is already applied before the merge.

Method and limits

How this was derived, and what it cannot claim

Local Claude and Codex transcripts were captured into a private SQLite database (385,404 raw records, 2.4 GB) and frozen at a watermark. From 44,592 candidate user messages, tool results, injected context, subagent and automated sessions were excluded, and near-simultaneous duplicates of the same prompt were reconciled, leaving 7,882 likely human prompts; 126 remain explicitly uncertain. A local model (qwen3.5:4b on loopback) labelled relevance; a deterministic pass then searched every prompt for explicit phrasings, twelve from the original hypothesis and thirteen taken from the corpus itself.

Three caveats travel with every number here. A phrase match is not a guideline — it can be a question, a quote or a correction. A missing match is not an absent preference, because wording varies and the corpus is typed fast. And the ranking measures what had to be said, which correlates with what matters but also with what agents kept getting wrong. No prompt text is published: the corpus never leaves the machine that collected it, and this page reports counts, not content.

The counter-analysis is not derived from the corpus — it is the argument from the other side, written against it. Absence in a prompt log is weak evidence about a person's real practice, and some of these gaps may be covered by habits that were never typed to an agent.
